# Операционная система реального времени без стеков

## Задача

При разработке небольших операционных систем реального времени для микроконтроллеров класса Arduino приходится особенно тщательно расходовать оперативную память. Для микросхемы ATmega328P, например, доступно всего 2 Кбайт ОЗУ.

Возникает естественный вопрос: нельзя ли построить многозадачную систему так, чтобы каждой задаче не требовался собственный стек?

Ниже описывается один из возможных вариантов такой системы. В ней отсутствуют стеки задач и динамическая память, а единственный системный вызов фактически не является функцией. В основе лежит механизм сопрограмм без стека (stackless coroutines).

Следует сразу оговориться: описываемый вариант предполагает расширение языка C. Современные компиляторы C такого средства пока не имеют. Предлагается дополнить язык средствами нативных сопрограмм, а уже на их основе построить небольшую ОС реального времени. Оба проекта пока являются рабочими предложениями.

## Обычная программа и возникающая проблема

Типичная первая программа для Arduino имеет весьма простой вид: включить светодиод, подождать 500 мс, выключить его и повторить операцию.

Но достаточно добавить ещё две задачи. Например, необходимо опрашивать датчик каждые 100 мс и одновременно принимать команды через последовательный порт.

Обычный вызов `delay()` в этом случае уже непригоден: во время задержки остальные операции не выполняются, и входной буфер последовательного порта может переполниться.

Стандартное решение состоит в отказе от блокирующих задержек и построении явной машины состояний:

```c
void loop() {
    u32 now = millis();
    if (now - led_last >= 500)     { led_last = now;    toggle_led(); }
    if (now - sensor_last >= 100)  { sensor_last = now; read_sensor(); }
    if (Serial.available())        { handle_byte(Serial.read()); }
}
```

Для двух-трёх операций такой подход вполне приемлем. Но с увеличением числа задач программа быстро усложняется. Управление каждой задачей приходится представлять отдельными переменными и состояниями. Особенно неудобно это становится при реализации протоколов.

Например, естественная последовательность

> принять три байта, дождаться подтверждения, затем в течение секунды ожидать ответ

превращается в машину состояний с множеством переходов вроде `WAITING_FOR_ACK_2`.

Между тем хотелось бы записать программу непосредственно в том порядке, в каком она должна выполняться:

```text
включить светодиод;
ждать 500 мс;
изменить состояние светодиода;
...
```

и предоставить операционной системе возможность выполнять в это время другие задачи.

## Почему обычная ОС реального времени здесь неудобна

Для такой работы естественно воспользоваться RTOS. Например, FreeRTOS предоставляет именно необходимые средства. Однако на малом микроконтроллере стоимость этих средств оказывается слишком высокой.

В ATmega328P имеется всего 2 Кбайт оперативной памяти.

Обычная многозадачная система выделяет каждой задаче собственный стек. Чтобы приостановить выполнение функции, необходимо сохранить регистры процессора и переключить указатель стека на стек другой задачи.

Даже практически пустая задача требует порядка 100–200 байт стека. Размер приходится задавать заранее:

```c
xTaskCreate(blink_task, "blink", 128, NULL, 1, NULL);
```

Если задач несколько, значительная часть ОЗУ быстро расходуется только на их стеки. Но существует и другая опасность. Если размер стека выбран слишком малым, задача не получает какого-либо аккуратного сообщения об ошибке: стек выходит за отведённую область и начинает портить соседние данные. Результат обычно проявляется самым неожиданным образом.

Поэтому возникает основной вопрос:

**можно ли приостановить выполнение функции, не предоставляя ей собственного стека?**

Оказывается, можно.

## Сопрограмма без стека

Идея stackless coroutine далеко не нова. Сопрограмма такого типа может быть приостановлена и впоследствии продолжена, но её состояние хранится не в отдельном стеке, а в небольшой структуре данных.

Обычный стек можно представить себе как рабочее место, закреплённое за каждой задачей. Сопрограмма использует это место только во время работы. При остановке она сохраняет небольшую «закладку»: где продолжить выполнение и какие данные необходимо сохранить.

Предлагаемый синтаксис может выглядеть следующим образом:

```c
coro(int) void counter(int limit) {
    for (int i = 0; i < limit; i++)
        yield i;
}
```

Запись `coro(int) void` означает, что функция является сопрограммой, выдающей значения типа `int` и не возвращающей обычного результата.

Оператор `yield` приостанавливает её выполнение. Возобновлением занимается вызывающая сторона:

```c
coro_frame(counter) f;
co_init(&f, counter, 10);

while (co_resume(&f) == CO_SUSPENDED)
    print_int(co_value(&f));
```

Здесь `f` — обычная переменная. Для хранения состояния сопрограммы не требуется обращаться к динамической памяти. Размер структуры может определить компилятор: ему известно, какие локальные переменные должны сохраняться через точку приостановки.

## Что должен делать компилятор

Рассмотрим более существенный пример — задачу управления светодиодом:

```c
coro(sys_req *) void blink(u8 pin, u16 period) {
    gpio_mode(pin, GPIO_OUT);

    for (;;) {
        gpio_toggle(pin);
        os_sleep_ms(period);
    }
}
```

После преобразования компилятором эта программа в общих чертах превращается в структуру состояния и функцию продолжения:

```c
struct blink__frame {
    u16 state;
    u8  pin;
    u16 period;
    sys_req req;
};

co_status blink__resume(struct blink__frame *f, co_signal sig) {
    switch (f->state) {
    case 0:
        gpio_mode(f->pin, GPIO_OUT);

        for (;;) {
            gpio_toggle(f->pin);

            f->req = (sys_req){
                .op = SYS_SLEEP,
                .u.sleep.deadline = os_now() + f->period
                            };

            f->state = 1;
            return CO_SUSPENDED;

    case 1:
            if (sig == CO_CANCEL)
                return CO_DONE;
        }
    }
}
```

Важная деталь состоит в том, что метка `case 1` находится непосредственно внутри цикла. Это известный приём, применявшийся, в частности, в protothreads Адама Данкелса. Существенное отличие предлагаемого варианта состоит в том, что преобразование выполняет компилятор, поэтому он может автоматически поместить в кадр сопрограммы те локальные переменные, которые действительно должны пережить приостановку.

В результате состояние задачи на ATmega может занимать примерно 16 байт:

```text
    blink__frame

    +------------------------------+
    | state       2 байта          |
    | pin         1 байт           |
    | period      2 байта + padding|
    | req        10 байт           |
    +------------------------------+
```

Таким образом, вместо порядка двухсот байт требуется около шестнадцати.

Причём размер кадра определяется компилятором, а не программистом.

Основное правило здесь следующее: **локальные переменные, не пересекающие точку приостановки, остаются в обычном стеке процессора и в кадр сопрограммы не попадают**. Поэтому счётчик цикла, используемый между двумя точками `yield`, дополнительной памяти не требует.

## Блокирующая операция как системный запрос

Теперь можно сделать следующий шаг.

Пусть каждая задача является сопрограммой, выдающей указатель `sys_req *`. Тогда всякая блокирующая операция представляется одинаковым образом:

1. формируется структура запроса;
2. её адрес передаётся операционной системе;
3. сопрограмма приостанавливается;
4. после выполнения запроса задача возобновляется.

Структура запроса может иметь следующий вид:

```c
struct sys_req {
    sys_req *next;
    u8       op;
    u8       flags;
    i16      out;

    union {
        struct {
            u32 deadline;
        } sleep;

        struct {
            os_chan *ch;
            void *msg;
        } chan;

        struct {
            u8 dev;
            u8 *buf;
            u16 len;
        } io;
    } u;
};
```

На AVR такая структура занимает порядка 10–12 байт.

Ожидание времени — запрос. Приём сообщения — запрос. Ожидание байта от UART, завершения преобразования АЦП или нажатия кнопки — также запрос.

Тем самым отпадает необходимость в двух различных механизмах — одном для «системных вызовов», другом для драйверов и ожиданий. Все блокирующие операции имеют одну и ту же природу.

Например, задержка на 100 мс в развёрнутом виде выглядит так:

```c
sys_req r = {
    .op = SYS_SLEEP,
    .u.sleep.deadline = os_now() + 100
};

yield &r;
```

А запись

```c
os_sleep_ms(100);
```

может быть просто макросом, разворачивающимся в эти две операции.

Обратное правило столь же важно: **операции, которые не могут блокировать выполнение, остаются обычными функциями**.

Например, `gpio_write()` фактически является записью в регистр. Превращать её в сопрограмму не имеет смысла: это лишь увеличило бы программу и замедлило её работу.

Таким образом, граница интерфейса получается весьма простой:

* операция, способная заблокировать задачу, является системным запросом;
* неблокирующая операция остаётся обычной функцией.

## Динамическая память операционной системе не нужна

Здесь обнаруживается ещё одно важное преимущество.

Структура `sys_req` является локальной переменной задачи и находится в её кадре. Приостановленная задача не перемещает этот кадр.

Поэтому ядру не требуется выделять отдельную структуру для ожидающей задачи. Если задача ожидает сообщение в канале, ядро просто включает уже существующий `sys_req` в список ожидающих, используя поле `next`.

Очередь ожидающих требует от канала всего одного указателя. Очередь таймеров строится тем же способом; элементы располагаются в порядке времени срабатывания.

Память ядра в таком варианте состоит из небольшого массива управляющих структур задач — около 8 байт на задачу — и примерно двадцати байт глобальных данных.

Например, восемь задач, три канала и несколько групп событий должны занимать около 400 байт. Для системы со стеком каждой задачи такой объём памяти был бы недостижим.

## Планировщик

Сам планировщик при этом оказывается чрезвычайно простым:

```c
void os_run(void) {
    os_init_all();

    for (;;) {
        os_tcb *t = highest_priority_ready();

        if (!t) {
            os_idle();
            continue;
        }

        if (t->resume(t->frame, CO_CONTINUE) == CO_DONE) {
            t->state = OS_DONE;
            continue;
        }

        t->pending = co_value_of(t);
        os_service(t);
    }
}
```

Алгоритм состоит из нескольких операций.

Планировщик выбирает готовую задачу с наивысшим приоритетом и возобновляет её. Затем он анализирует полученный от неё запрос.

Если запрос может быть выполнен немедленно — например, истёк заданный интервал времени или в канале уже имеется сообщение, — задача снова становится готовой.

Если выполнить запрос пока невозможно, его структура включается в соответствующую очередь, а задача переводится в состояние ожидания.

Особенно интересен режим простоя.

Когда готовых задач нет, `os_idle()` определяет ближайший момент, когда должна произойти следующая операция, программирует аппаратный таймер и переводит микроконтроллер в режим сна.

Периодического системного тика при этом нет.

Если все задачи ожидают по 500 мс, процессор просыпается два раза в секунду, а не тысячу раз в секунду.

## Обработка прерываний

Обработчики аппаратных прерываний остаются обычными функциями. Они не являются сопрограммами и не могут выполнять `yield` или блокирующие операции ОС.

Для обработчика прерывания предусмотрены только три операции:

```c
void os_isr_post(os_events *ev, os_events bits);
bool os_isr_send(os_chan *ch, const void *msg);
void os_isr_wake(os_task *t);
```

Все они должны выполняться за постоянное время и не используют динамическую память.

Принцип здесь прост: **обработчик прерывания только переводит задачу в состояние готовности, но не выполняет работу вместо неё**.

Например, обработчик UART может быть очень коротким, а собственно обработка поступивших данных выполняется отдельной задачей, которую это прерывание пробуждает.

## Большинство блокировок оказывается ненужным

Из выбранной организации задач следует ещё одно интересное следствие.

Задача выполняется непрерывно от одной точки приостановки до следующей. Другая задача в этот промежуток её не прерывает.

Отсюда:

**критическая секция, внутри которой нет `yield`, не нуждается в блокировке.**

Например, изменение общей структуры данных, обход списка или операция чтение–изменение–запись над счётчиком являются атомарными относительно других задач.

Исключение составляют аппаратные прерывания. Для операций, которые должны быть защищены и от них, предусматривается отдельная конструкция:

```c
OS_ATOMIC {
    ...
}
```

Тем самым значительная часть обычных операций с мьютексами исчезает.

При этом необходимые средства синхронизации сохраняются.

Например,

```c
OS_CHAN(readings, i16, 4)
```

создаёт статически заданный кольцевой буфер, через который можно блокирующе передавать и принимать сообщения.

Конструкция

```c
OS_EVENTS(uart_ev)
```

создаёт битовую маску событий, которую может устанавливать обработчик прерывания, тогда как задача может ожидать соответствующего события.

Мьютекс всё же необходим в случае, когда ресурс должен оставаться захваченным через точку приостановки. Типичный пример — длительная транзакция по I²C, внутри которой имеются операции ожидания.

## Пример полной программы

Ниже приведён пример программы, в которой работают три независимые задачи.

```c
#include <braam/rt.h>

OS_CHAN(samples, i16, 4);
OS_EVENTS(button_ev);

#define BTN_PRESSED (1u << 0)

ISR(PCINT0_vect) {
    os_isr_post(&button_ev, BTN_PRESSED);
}

coro(sys_req *) void sensor(u8 ch, u16 period) {
    u32 next = os_now();

    for (;;) {
        i16 v = os_adc_read(ch);
        os_try_send(&samples, &v);

        next += period;
        os_sleep_until(next);
    }
}

coro(sys_req *) void reporter(void) {
    for (;;) {
        i16 v;

        i16 r = os_deadline(2000, os_recv(&samples, &v));

        if (r == OS_ETIMEDOUT) {
            os_uart_write(0, "stall\n", 6);
            continue;
        }

        u8 line[8];
        os_uart_write(0, line, fmt_i16(line, v));
    }
}

coro(sys_req *) void on_button(void) {
    for (;;) {
        os_wait_any(&button_ev, BTN_PRESSED);
        gpio_toggle(13);
        os_sleep_ms(50);
    }
}

OS_TASK(t_sensor,   sensor,    1, 0, 100);
OS_TASK(t_reporter, reporter,  1);
OS_TASK(t_button,   on_button, 3);

OS_TASKS(&t_sensor, &t_reporter, &t_button);

int main(void) {
    os_run();
}
```

Первая задача периодически получает данные от АЦП и передаёт их в канал. Вторая принимает измерения и передаёт их через UART. Третья ожидает события от кнопки.

Все три задачи записаны непосредственно в виде алгоритмов. В программе нет стеков задач, динамической памяти и периодического системного тика. В промежутках между событиями микроконтроллер может находиться в состоянии сна.

Потребляемая задачами память определяется компилятором и известна на этапе компоновки. Если программа не помещается в доступную память, ошибка обнаруживается при компоновке, а не после запуска устройства.

Обратим внимание также на конструкцию:

```c
os_deadline(2000, os_recv(&samples, &v))
```

Время ожидания не приходится добавлять отдельным параметром к каждой блокирующей операции. Установка предельного времени изменяет сам запрос, после чего ядро помещает его одновременно в очередь канала и очередь таймеров. Срабатывает тот источник, который произойдёт первым.

Таким образом, и здесь используется один и тот же механизм запросов.

## Цена такого решения

Разумеется, у предлагаемой системы есть ограничения.

Главное из них связано с тем, что планирование является кооперативным.

Если задача выполняется в течение 10 мс, не встречая ни одной точки `yield`, остальные задачи не смогут получить процессор в течение этих 10 мс. Принудительно прервать такую задачу данный вариант ОС не может.

Предусмотрен сторожевой таймер, который позволяет обнаружить зациклившуюся задачу и перезапустить систему с выдачей информации об ошибке. Но обнаружение ошибки не устраняет её. Если требуется гарантированная реакция быстрее, чем максимальный интервал между двумя точками приостановки, соответствующую работу следует выполнять непосредственно из обработчика прерывания.

Есть и второе ограничение.

Обычная вспомогательная функция не может внезапно заблокироваться. Если функция потенциально выполняет `yield`, она сама должна быть сопрограммой, а её вызов должен выполняться соответствующим образом, например через `await`.

Таким образом, разделение на синхронный и асинхронный код распространяется вверх по цепочке вызовов. Это та цена, которую приходится платить за отказ от отдельных стеков задач. Выигрыш — существенное сокращение требуемой оперативной памяти.

## Заключение

Предложенная конструкция пока не является готовой реализацией. Операторы `coro`, `yield` и `await` отсутствуют в современном языке C.

Но сама схема достаточно проста, чтобы её можно было рассматривать как конкретное предложение по организации небольшой ОС реального времени:

* каждая задача представляет собой сопрограмму;
* отдельного стека у задачи нет;
* состояние задачи хранится в небольшом кадре;
* всякая блокирующая операция представляется системным запросом;
* запрос хранится непосредственно в кадре задачи;
* ядро не использует динамическое выделение памяти;
* планирование является кооперативным;
* обработчики прерываний остаются короткими и неблокирующими;
* при отсутствии работы процессор может непосредственно переходить в состояние сна.

Ближайшим практическим подтверждением жизнеспособности такой архитектуры является Embassy — система для Rust, реализующая по существу тот же принцип и применяемая в реальных устройствах.

Предлагаемое расширение C состоит из двух частей. Первая описывает средства языка: два ключевых слова, один конструктор типа и семь операций без скрытого выделения памяти. Вторая определяет устройство самой ОС: протокол системных запросов, планировщик, драйверы, отмену операций и расход памяти.

Главная идея, однако, значительно проще всех этих деталей.

**Если задаче для продолжения работы не нужен весь её стек, незачем хранить весь стек. Достаточно сохранить небольшое состояние и точку, с которой следует продолжить вычисление.**

А если всякое ожидание представить как передачу ядру запроса с последующим `yield`, то даже весьма скромный микроконтроллер получает многозадачную систему, в которой программа сохраняет обычную последовательную форму, а основная работа по переключению задач выполняется компилятором и небольшим ядром.
